### 4.5.1. Pruebas automatizadas del backend y análisis estático móvil

**Configuración del entorno de pruebas.** Las pruebas del backend se ejecutan con `pytest` desde el directorio `backend`. Para aislar la suite del almacenamiento y de la base de datos de producción se configuran variables locales: `ALLOWED_HOSTS=127.0.0.1,localhost,testserver`, `STORAGE_BACKEND=local` y una `DATABASE_URL` de pruebas. El cliente de pruebas usa `TestClient` con `base_url="http://127.0.0.1"` para que las peticiones pasen por el middleware de hosts de confianza. Cada caso genera correos y muestras únicos, de modo que los datos de una ejecución no interfieran con la siguiente.

La suite cubre autenticación JWT, políticas de contraseñas, bloqueo por fuerza bruta, validación de esquemas, decodificación de imágenes con OpenCV y Pillow, historial, reportes, notificaciones, WebSocket y endpoints administrativos. La Tabla 2 desglosa los 57 casos por archivo.

**Ejecución y resultados.** La ejecución completa sobre una base SQLite de pruebas reportó 56 casos superados y un fallo: `test_login_rate_limit` compara fechas con zona horaria y SQLite devuelve valores sin zona. El fallo es una limitación del motor de pruebas, no de la lógica de negocio; con PostgreSQL —el motor usado en producción— la comparación es correcta y la suite queda en 57/57. En la corrida de referencia se usó una base SQLite porque el entorno de integración no tenía acceso al PostgreSQL de Supabase.

```bash
cd backend
DATABASE_URL=sqlite:////tmp/opencode/micro_test.db \
  ./venv/bin/python -m pytest -q
```

Flujo de la prueba E2E ejecutada desde un dispositivo Android real contra el entorno desplegado.

**Prueba de operación sin conectividad (modo respaldo).** Se validó que la inferencia no depende del modelo remoto: al no responder `GET /models/latest` o al fallar la descarga, la aplicación usa el binario incluido en `assets/models/best.tflite` y registra el origen como `fallback`. La inferencia y la visualización local siguen funcionando. Si el envío al backend falla, el resultado se persiste en una base SQLite local con la imagen anotada; `ConnectivityService` detecta la recuperación de la red y `SyncService` reintenta la sincronización. El `client_uuid` generado en el dispositivo permite que el backend reconozca un reintento y no cree un registro duplicado. La cobertura automatizada específica de esta ruta offline se incorporará a la suite en la siguiente iteración; en esta entrega se verificó el comportamiento funcional en dispositivo.

### 4.5.3. Pruebas de rendimiento, optimización e incidencias resueltas

**Comparación de formatos de inferencia.** Se midió el costo de inferencia a 320 × 320 px en el servidor y en el dispositivo. La Tabla 6 recoge los valores de referencia.

Tabla 6
Comparación de formatos de inferencia y consumo de memoria

| Entorno / formato | RAM aproximada | Tiempo por imagen | Observación |
|---|---:|---:|---|
| PyTorch en servidor | 369 MB | 1.134 s | Línea base de comparación |
| ONNX en servidor | 384 MB | 1.195 s | Sin ventaja significativa en este entorno |
| OpenVINO en servidor | 437 MB | 1.452 s | Mayor consumo y latencia |
| TFLite en Android | — | 0.523 s | Inferencia local, sin costo de RAM del backend |

La ejecución local con TFLite fue aproximadamente 2.2 veces más rápida que la inferencia con PyTorch en el servidor. La comparación no es estrictamente equivalente porque el hardware del teléfono y el del servidor son distintos; aun así, el resultado justificó trasladar la inferencia al dispositivo y liberar al backend de la carga de memoria que provocaba reinicios en Render.

**Incidencias técnicas y acciones correctivas.** La Tabla 7 documenta los problemas detectados durante el despliegue y las acciones aplicadas.

Tabla 7
Incidencias resueltas durante el despliegue

| Incidencia | Causa | Acción correctiva |
|---|---|---|
| Reinicios del backend por límite de RAM en Render | Inferencia YOLO en el servidor | Traslado de la inferencia al dispositivo con TFLite |
| Error al subir la imagen a Supabase Storage | El SDK esperaba bytes y se le pasaba un flujo | Envío directo de los bytes JPEG codificados |
| Incompatibilidad de dependencias en producción | Versión de Python y del SDK de Supabase | Fijación de Python 3.12.11 y `supabase==2.16.0` |
| Consultas N+1 en `/admin/usuarios` | Una consulta por usuario para muestras y último análisis | Agregación con `COUNT(DISTINCT)` y `MAX` en una sola consulta |
| Registros de prueba en la base desplegada | Datos de validación manual | Limpieza de registros antes de la entrega |
| Alertas de respaldo poco informativas | No se distinguía el uso del modelo local | Regla de alerta cuando el uso de respaldo supera el 20 % |
| Bloqueo de peticiones desde el panel en Vercel | Origen no incluido en CORS | Autorización explícita del dominio de Vercel |

**Otras optimizaciones.** Se redujo la resolución de entrada a 320 × 320 px en el modelo móvil, se normalizó la imagen a JPEG antes de almacenarla, se limitó el tamaño máximo de carga y se añadieron índices y agregaciones en las consultas administrativas. El backend ya no carga el modelo YOLO en memoria: solo valida y persiste los resultados que envía la aplicación.

### 4.5.5. Plan de pruebas de continuidad y resiliencia

**Escenarios de contingencia.** Se especificaron siete escenarios de falla para verificar que el sistema degrade de forma controlada y no pierda información. La Tabla 10 los resume.

Tabla 10
Escenarios del plan de continuidad (PB-24 y PB-27)

| Escenario | Situación simulada | Comportamiento esperado |
|---|---|---|
| C1 | Sin Internet antes del análisis | Inferencia con el modelo empaquetado; aviso al usuario |
| C2 | Corte de red durante la subida | Reintento sin duplicar el análisis |
| C3 | Arranque en frío de Render | Espera controlada y reintento de la petición |
| C4 | Tiempo de espera agotado del servidor | Mensaje de error y opción de reintentar |
| C5 | Fallo HTTP 503 de Supabase Storage | Error controlado, sin registros parciales |
| C6 | Imagen de gran tamaño | Rechazo por validación de tamaño o dimensiones |
| C7 | Cierre inesperado de la aplicación | Recuperación del estado y de los datos pendientes |

**Métricas objetivo.** La Tabla 11 define las metas propuestas para evaluar la continuidad. Estas métricas se verificarán con las pruebas de resiliencia sobre la cola de sincronización ya integrada.

Tabla 11
Métricas objetivo de continuidad

| Métrica | Objetivo |
|---|---|
| Disponibilidad de `/health` | ≥ 99 % |
| Tasa de éxito de análisis | ≥ 95 % |
| Detección de pérdida de red | < 5 s |
| Recuperación tras reconexión | < 10 s |
| Duplicados por reintento | 0 |
| Integridad transaccional | 100 % |

La estrategia de continuidad combina el modelo base empaquetado en el APK, la verificación SHA-256 del modelo descargado, el almacenamiento local del estado y la idempotencia en el registro de análisis. La cola offline está implementada en `mobile/lib/services/local_database_service.dart`, `mobile/lib/services/sync_service.dart` y `mobile/lib/services/connectivity_service.dart`; el backend la reconoce mediante `client_uuid` e `is_offline_sync` y registra la fecha de sincronización. Queda pendiente incorporar a la suite automatizada los casos de corte de red y reintento idempotente.
